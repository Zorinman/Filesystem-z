# 普通上传交互过程
普通上传由客户端一次发送完整文件。

```text
用户选择文件一次
    ↓
客户端后台发送完整文件
    ↓
服务端接收、计算 SHA1 并暂存
    ↓
服务端保存文件（必要时异步转存 OSS）及数据库记录
    ↓
客户端显示上传结果
```
1. **发送完整文件**  
   用户选择文件一次 →  
   客户端后台将完整文件及用户名等表单信息发送至 `/file/upload` →  
   服务端接收完整文件并读取内容 →  
   服务端计算文件 SHA1、记录原始文件名和文件大小 →  
   服务端将文件写入本地临时存储。

2. **保存文件并响应**  
   服务端根据存储配置将文件写入目标存储；启用异步转存时，先发布 OSS 转存任务 →  
   服务端保存文件元数据和用户文件记录 →  
   异步模式下，后台转存服务稍后将本地临时文件上传到 OSS，并更新文件存储地址 →  
   服务端返回上传结果（根入口成功后重定向到文件列表；微服务入口返回 JSON）→  
   客户端显示结果。


# 分块上传功能模块解析
该功能尚未整合到Html前端页面，只是使用`test_mpupload.go`模拟前端单独测试


`mpupload.go`实现服务端功能
`test_mpupload.go`模拟客户端 
`Redis`作为缓存存储分块上传的状态信息，
其中创建一个键名为`UploadID`的哈希表，哈希表中存储的状态信息有`chunkcount`（文件分块的总数），`filehash`，`filesize`，`chkidx_<chunkIndex>`（每个分块的索引ID）


## 模块概述
分块上传功能模块主要用于处理大文件的上传需求，通过将文件分割成多个小块并逐块上传，解决了大文件上传过程中可能出现的网络不稳定、传输中断等问题。该模块的主要功能包括：

1. 初始化分块上传。
2. 上传文件分块。
3. 合并分块并完成上传。

过程：
### 分块上传的交互过程
```text
用户选择文件一次
    ↓
客户端后台初始化任务并取得分块规则
    ↓
客户端自动拆分、上传并重试分块
    ↓
服务端校验分块并记录 Redis 状态
    ↓
客户端请求完成
    ↓
服务端合并、校验完整文件并保存
    ↓
客户端显示上传结果
```

客户端通过`resp, err := http.PostForm(请求内容以及携带的值信息)`像服务端发送请求

服务端返回的结果存储在`resp.Body`中供客户端读取

1. **初始化分块上传**  
   客户端发送初始化请求到服务端 →  
   服务端解析请求参数，生成 `UploadID` 和分块信息 →  
   服务端将分块信息存储到 Redis（如分块总数、文件哈希值、文件大小等） →  
   服务端返回 `UploadID` 和分块信息给客户端。

2. **上传文件分块**  
   客户端根据返回的信息将文件进行分块划分并生成`index`(都在`multipartUpload`内完成)之后发送分块上传请求到服务端 →  
   服务端解析请求参数，生成分块文件存储路径并写入分块数据 →  
   服务端在 Redis 中更新分块上传状态（标记分块已上传） →  
   服务端返回上传结果给客户端 →  
   客户端继续上传下一个分块，直到所有分块上传完成。

3. **合并分块并完成上传**  
   客户端通过 `multipartUpload` 函数中的`ch`通道机制确认收到所有分块上传完成的结果后开始发送合并请求到服务端 →  
   服务端解析请求参数，查询 Redis 中的分块状态，验证所有分块是否上传完成 →  
   服务端调用 `mergeChunks` 函数合并分块文件为完整文件 →  
   服务端删除分块文件并更新数据库（如用户文件表和唯一文件表） →  
   服务端删除 Redis 中的分块状态，释放内存 →  
   服务端返回合并结果给客户端。

## `mpupload.go`服务端功能解析
## 核心结构
模块中定义了一个核心结构体 `MultipartUploadInfo`，用于存储分块上传的相关信息：

- `FileHash`：文件的哈希值，用于唯一标识文件。
- `FileSize`：文件的总大小。
- `UploadID`：上传任务的唯一标识符。
- `ChunkSize`：每个分块的大小。
- `ChunkCount`：分块的总数。





### 1. 初始化分块上传
**函数：`InitialMultipartUploadHandler`**
- 解析用户请求参数，包括用户名、文件哈希值和文件大小。
- 通过 Redis 连接池获取一个连接。
- 生成分块上传的初始化信息，包括分块大小（默认 5MB）和分块总数。
- 将初始化信息存储到 Redis 中，键名格式为 `MP_<UploadID>`，存储内容包括分块总数、文件哈希值和文件大小。
- 返回初始化信息（如 `UploadID` 和分块信息）给客户端。

### 2. 上传文件分块
**函数：`UploadPartHandler`**
- 解析用户请求参数，包括 `uploadid` 和分块索引 `index`。
- 通过 Redis 连接池获取一个连接。
- 根据 `uploadid` 和分块索引生成分块文件的存储路径，并创建必要的目录。
- 打开文件句柄，将分块数据写入文件，支持分块数据流式写入。
- 更新 Redis 中的分块上传状态，键名格式为 `chkidx_<index>`，值为 `1` 表示该分块已上传。
- 返回上传结果（成功或失败）给客户端。

### 3. 合并分块并完成上传
**函数：`CompleteUploadHandler`**
- 解析用户请求参数，包括 `uploadid`、用户名、文件哈希值、文件大小和文件名。
- 通过 Redis 连接池获取一个连接。
- 查询 Redis 中的分块上传状态，验证所有分块是否上传完成。
- 调用 `mergeChunks` 函数合并分块文件为完整文件，合并完成后删除分块文件以节省存储空间。
- 更新数据库，包括唯一文件表和用户文件表，记录文件上传信息。
- 返回处理结果（成功或失败）给客户端。

**函数：`mergeChunks`**
- 按顺序读取所有分块文件并将其内容写入目标文件。
- 合并完成后删除分块文件以节省存储空间。
- 如果在合并过程中发生错误，返回错误信息。


# (重要) 分块上传优化：
当前项目通过“临时分块文件**写入流程结束 + Redis 标记 chkidx_index = 1**”判断分块成功，但这个判断不够严格，即使磁盘写入失败，代码仍可能把该分块标记为已完成。

应该加入对于**分块大小**和**分块哈希**的校验，确保分块数据完整性。
**一个分块接收成功的判断改为**：
```txt
+ 写入分块字节数正确
+ 分块哈希校验值正确
+ 写入过程无错误
+ 文件关闭成功
+ Redis 状态更新成功
```
**具体流程如下**：
```txt
第 0 块：
    客户端提供 chunkHash[0]和 chunkSize[0]
    服务端接收后重新计算 chunkHash[0]和检查chunkSize[0]
    两者比较

第 1 块：
    客户端计算 chunkHash[1]和 chunkSize[1]
    服务端接收后计算 chunkHash[1]和检查chunkSize[1]
    两者比较
```

**最终职责如下，标记部分为新增**：
客户端：
    `提供每个分块哈希和每个分块大小`
    和完整文件大小和完整文件哈希

服务端：
    `验证实际接收分块大小`
    `重新计算并对比验证每个分块哈希`
    合并后重新计算并对比验证完整文件哈希
    以服务端验证结果为准

## Redis优化：
**当前只用了一个Hash结构**
所以当前的 Redis 结构是：
```txt
一个上传任务
    ↓
一个 Hash
    ├── 文件基本信息
    ├── 分块总数
    ├── 文件总大小
    └── 所有分块完成标记
```
Key 的格式是：MP_{uploadID}
这个 Key 对应一个 Redis Hash，内部保存多个字段：
| Field        |       Value | 含义                   |
| ------------ | ----------: | ---------------------- |
| `chunkcount` |        `27` | 服务端计算出的分块总数 |
| `filehash`   | `abc123...` | 客户端提交的文件哈希   |
| `filesize`   | `132489256` | 文件总大小             |
| `chkidx_0`   |         `1` | 第 0 个分块已上传      |
| `chkidx_1`   |         `1` | 第 1 个分块已上传      |
| `chkidx_2`   |         `1` | 第 2 个分块已上传      |

为了满足以上的优化需求，Redis 结构改为2个Hash结构，**两个结构的 Key为同一个 uploadID**：
| 结构                 | Redis 类型 | 作用         | 内容范围                   |
| -------------------- | ---------- | ------------ | -------------------------- |
| `upload:{id}:meta`   | Hash       | 管理上传任务 | 文件整体和任务状态         |
| `upload:{id}:chunks` | Hash       | 管理分块状态 | 每个分块的大小、哈希和状态 |

>客户端每次上传分块时提交分块哈希和分块大小，服务端比较通过后不再单独在Redis中保存。redis仅保存客户端提供的关于整个文件的信息，即文件哈希值`client_file_hash`和文件大小`expected_file_size`

**上传任务 Hash：upload:{uploadID}:meta**
| Field                | 作用                                       |
| -------------------- | ------------------------------------------ |
| `status`             | 上传任务状态                               |
| `username`           | 任务所属用户                               |
| `filename`           | 原始文件名                                 |
| `hash_algorithm`     | 哈希算法                                   |
| `client_file_hash`   | 客户端提交的完整文件哈希                   |
| `server_file_hash`   | 服务端合并后计算的完整文件哈希             |
| `server_chunk_size`  | 服务端确定的基础分块大小（字节）           |
| `server_chunk_count` | 服务端计算的分块总数                       |
| `received_file_size` | 已验证分块的实际大小之和（字节）           |
| `expected_file_size` | 客户端声明、服务端接受的文件总大小（字节） |
| `verified_count`     | 已验证分块数量                             |
| `created_at`         | 任务创建时间                               |
| `expires_at`         | 任务业务过期时间，不替代 Redis TTL         |

**分块详情 Hash：upload:{uploadID}:chunks**
>注意：冒号只是普通字符，不代表嵌套结构或 Redis 的特殊语法，所以每一个分块都有3三个Field，如果有N个分块，就会有Nx3个Field。
| Field                       | 作用                             |
| --------------------------- | -------------------------------- |
| `chunk:{index}:status`      | 当前分块状态                     |
| `chunk:{index}:server_size` | 已验证分块的实际写入大小（字节） |
| `chunk:{index}:server_hash` | 服务端计算的分块哈希             |

##  优化后的分块上传交互过程（方案）
用户拖入或选择文件一次后，客户端在后台自动完成以下请求；“一次操作”不代表只发送一次 HTTP 请求。

```text
用户选择文件一次
    ↓
客户端后台初始化任务并取得分块规则
    ↓
客户端自动拆分、上传并重试分块
    ↓
服务端校验分块并记录 Redis 状态
    ↓
客户端请求完成
    ↓
服务端合并、校验完整文件并保存
    ↓
客户端显示上传结果
```

1. **初始化上传任务**  
   客户端读取文件名、总大小并计算完整文件哈希 →  
   客户端发送初始化请求，提交文件名、总大小和完整文件哈希 →  
   服务端验证参数、确定分块大小并计算分块数量 →  
   服务端在 Redis 的 `upload:{uploadID}:meta` Hash 中保存任务元数据和状态 →  
   服务端返回 `uploadID`、分块大小和分块数量 →  
   客户端按服务端返回的规则拆分文件。

2. **上传并校验分块**  
   客户端计算当前分块的大小和哈希，并发送分块内容、序号、大小及哈希 →  
   服务端根据任务元数据和分块序号计算该块预期大小 →  
   服务端接收分块、写入临时文件，并计算实际写入大小和分块哈希 →  
   服务端校验实际大小与预期大小一致，且服务端哈希与客户端哈希一致 →  
   服务端确认文件写入及关闭成功后，在 Redis 的 `upload:{uploadID}:chunks` Hash 中记录分块状态、实际大小和服务端哈希，并更新任务进度 →  
   服务端返回该分块结果 →  
   客户端按需并发上传其他分块，并对失败分块重试。

3. **合并并校验完整文件**  
   客户端确认所有分块请求成功后，发送完成请求 →  
   服务端检查 Redis 中的分块状态和数量，并确认已验证分块的大小总和等于预期文件总大小 →  
   服务端按序合并临时分块，同时计算完整文件哈希 →  
   服务端比较完整文件哈希与初始化时客户端提交的哈希 →  
   校验通过后，服务端保存文件元数据并按存储配置同步上传或异步转存 OSS →  
   异步模式下，转存服务从本地临时文件上传到 OSS，完成后更新文件存储地址 →  
   服务端更新任务状态并清理分块文件及 Redis 任务数据；合并后的临时文件保留至异步转存服务处理完成 →  
   服务端返回最终结果给客户端。
